# 지급 작업 적체를 신규 주문 접수 gate에서 분리

- 제안일: 2026-11-29
- 상태: 채택 (2026-11-29, 개인 fork 개선 작업. 팀 결정 절차 없음). 구현·재측정 전
- 범위: Commerce 신규 주문 접수 gate([업무 정책](../policies.md#신규-접수-제한과-재개))의 필수 관측 중 `settlement.payout_jobs`
- 연결 문서: [정산 일배치 범위·실행 시각](0007-settlement-batch-scope-and-schedule.md) D2, [Kafka 전달과 처리 용량](0005-kafka-event-delivery-and-capacity.md), [운영 알람](../policies.md#운영-알람)

## 배경

신규 주문 접수 gate는 새 금융 부하를 만드는 `POST /api/orders`를 막아 금융 파이프라인이 밀릴 때 더 쌓이지 않게 합니다. 필수 관측 대상은 코드에 고정되어 있고(`OrderAdmissionConfiguration`), 여기에 Settlement의 지급 작업 `settlement.payout_jobs`도 들어 있습니다. 어떤 대기열이든 **실행이 도래한 미처리 건의 최장 지연이 60초 이상**이면 접수를 닫고, 모든 재개 조건이 60초 연속 유지되면 다시 엽니다.

정산 일배치(매일 10:00, [ADR 0007](0007-settlement-batch-scope-and-schedule.md) D2)는 지급 대상 항목을 선점한 판매자마다 지급 작업을 하나씩 만들며, 이 작업들은 `next_run_at = now`로 생성 즉시 실행이 도래합니다(`PayoutJob.schedule`). 따라서 지급 Worker가 배치가 만든 작업을 **60초 안에 모두 시작하지 못하면** 매일 10:00 직후 신규 주문 접수가 닫힙니다.

ADR 0007 D2는 10:00을 고른 이유 중 하나로 "부하 시험에서 일배치와 트래픽의 겹침을 자연스럽게 검증할 수 있다"를 들었고, 낮 트래픽과의 경합은 판매자별 짧은 트랜잭션이고 잠그는 행이 `PAYABLE` 항목이라 신규 원장 INSERT와 직접 충돌할 일이 적다고 보았습니다. 그 겹침 시험(S4)을 실제로 해 보니, 주된 상호작용은 DB 경합이 아니라 이 gate였습니다.

## 관측 (S4, 로컬 Mac·Compose)

- 조건: 주문 80 TPS(로컬 결제 처리 지속 상한 약 105건/초의 약 76%), 측정 시작 120초 뒤 S1-large 일배치(판매자 2만·항목 27만). 측정 도구 조건상 지급 Worker는 꺼 둠
- 결과: 배치 시작 84초 뒤 접수 gate가 닫힘
  - `commerce.order.admission state=CLOSED reason=THRESHOLD_EXCEEDED signal=DUE_AGE resource=settlement.payout_jobs value=65.9 limit=60.0`
  - 이후 측정 끝까지 신규 주문 전부 503 (C-warmup 55,634건)
- 같은 조건의 주문 단독(A)·배치 단독(B)은 오류 0

지급 Worker를 켠 운영 조건에서 닫힘 여부는 Worker 처리량이 지급 작업 생성 속도를 따라가는지에 달려 있습니다. 도래 지연은 가장 오래 기다린 도래 작업의 `next_run_at`(임대가 만료된 RUNNING 작업은 `lease_until`)부터 셉니다(`FinancialQueueMetrics`). Worker는 `next_run_at` 순으로 가져갑니다. 일배치는 S1-large에서 약 3분 동안 2만 건, 평균 약 110건/초로 지급 작업을 만듭니다. 개선 후 지급 Worker 처리량 실측(S5)으로 어림하면 다음과 같습니다(측정 아님).

| finance-mock 지급 응답 | 지급 Worker 처리량 (S5 실측) | 2만 건 소화 (배치 시작부터) | gate (도래 지연 60초 기준) |
| --- | --- | --- | --- |
| 0ms | 387건/초 | 배치와 함께 끝남 | 열림. 생성 속도보다 빨라 적체가 쌓이지 않음 |
| 100ms | 48건/초 | 약 7분 | 닫힘. 배치 시작 1~2분 뒤부터 소화 후 재개 대기 60초까지 약 6~7분 |
| 500ms | 11.2건/초 | 약 30분 | 닫힘. 약 30분 |

실은행·외부 송금 API의 응답은 0ms가 아니므로, 지금 설계대로면 **매일 10:00 직후 낮 시간에 수 분~수십 분 신규 주문이 막힌다**고 봐야 합니다.

## 문제

1. **막아도 적체가 줄지 않는다.** 신규 주문은 지급 작업을 만들지 않습니다. 지급 작업은 정상 경로에서 구매확정 뒤 다음 일배치가 만들고([ADR 0001](0001-payout-after-purchase-confirmation.md)), 그 밖에는 시연용 정산 실행과 운영자 재처리(`reopenForReplay`)뿐입니다. 주문을 막아도 지급 적체는 그대로이고, 접수 차단은 가용성만 잃습니다.
2. **적체의 원인이 정상 동작이다.** 하루치 지급을 한 시각에 만드는 것은 설계된 동작이고, 수 분 안에 소화되는 한 장애가 아닙니다. gate는 이를 장애처럼 다룹니다.
3. **같은 판단이 이미 알림에 적용되어 있다.** 정책은 "알림 전용 그룹·Job의 적체는 금융 gate의 건수·지연 조건에서 제외하고 별도 경보로 다룬다"고 정했습니다. 신규 주문이 만들지 않고, 주문을 막아도 줄지 않는 적체라는 점에서 지급 작업도 같습니다.

## 결정 (제안)

`settlement.payout_jobs`를 신규 주문 접수 gate의 필수 관측(`QUEUE_SIZE`·`DUE_AGE`)에서 뺍니다. 지급 적체는 기존 [운영 알람](../policies.md#운영-알람)의 **지급 지연**(확정 배치가 회차 마감 후 30분/60분 미지급, WARNING/CRITICAL)과 **금융 미확정**으로 다룹니다.

gate에 남는 것: Commerce·Payment·Settlement의 Kafka lag, Outbox·Inbox, `payment.payment_jobs`, 저장소 사용률, 관측 유효성. 신규 주문이 실제로 부하를 더하는 경로는 모두 그대로 감시합니다. Settlement의 Outbox·Inbox도 남기므로, 지급 처리가 Settlement를 전반적으로 막아 원장 반영이 밀리는 경우는 여전히 gate가 잡습니다.

## 검토한 안

| 안 | 판단 |
| --- | --- |
| A. `payout_jobs`를 gate에서 제외, 지급 지연 알람으로 감시 (제안) | 차단해도 줄지 않는 적체를 gate에서 뺌. 알림 제외와 같은 기준. 코드 변경이 목록 한 줄 |
| B. 대기열별 기준값을 두고 `payout_jobs`만 지연 기준을 30분으로 | 지급 지연 알람과 기준이 겹치고, 30분 넘게 밀려도 주문을 막아 봐야 줄지 않는다는 문제(1)는 그대로 |
| C. 일배치가 지급 작업의 실행 시각을 Worker 처리량에 맞춰 나눠 둠 | 도래 전 작업은 지연으로 세지 않으므로 gate는 열려 있음. 하지만 Worker 처리량을 배치가 알아야 하고, 실제 처리 여유가 있어도 지급이 인위적으로 늦어짐. 적체를 숨기는 방식 |
| D. 일배치를 03:00으로 이동 (ADR 0007 D2 재검토. D2는 팀 결정 항목이었음) | 낮 차단은 피하지만 gate는 여전히 닫힘. D2가 근무 시간을 고른 이유(즉시 대응)를 잃음 |
| E. 지급 Worker 처리량을 늘려 60초 안에 소화 | 외부 송금 응답 시간에 좌우되어 보장할 수 없음. 판매자 수가 늘면 다시 넘음 |

## 감수하는 점

- 지급 Worker가 멈추거나 극단적으로 밀려도 주문은 계속 받습니다. 이 상황은 지급 지연·금융 미확정 알람과 운영자 조치로 다룹니다. 주문을 막아서 해결되는 상황이 아니므로 받아들입니다.
- 이 변경 뒤 지급 적체는 알람으로만 드러납니다. 어림(측정 아님)하면 다음과 같습니다.
  - 0ms·100ms: 알람 없음. 100ms에서 FIFO 도래 지연의 최대는 약 235초로 **작업 적체** WARNING(300초) 아래이고, 약 7분 안에 소화되어 **지급 지연**(마감 후 30분)에도 닿지 않습니다.
  - 500ms: 시작 약 17분 뒤 **작업 적체 CRITICAL**(900초, `for` 없음)이 나고, 지급 지연 WARNING(30분)도 경계입니다. 즉 외부 응답이 이만큼 느리면 매일 10:00 직후 CRITICAL이 납니다.
  - 지급 작업을 작업 적체 알람에서 빼고 지급 지연 기준으로만 볼지는 별도로 정합니다(미결).
- gate가 Settlement DB·지급 Worker의 부하를 간접 신호로 쓰던 효과는 사라집니다. 공유 Postgres 경합은 다른 대기열 지연과 저장소 관측으로 잡히는지 S4 재측정으로 확인합니다.

## 검증

1. 변경 후 같은 S4 조건(C: 주문 80 TPS + S1-large 배치, 지급 Worker 꺼짐)을 다시 돌려 gate가 닫히지 않고 주문 503이 0인지 확인
2. 같은 측정으로 원래 S4 질문(H4 공유 Postgres 쓰기 경합, H5 Commerce 호출 경합)과 주문 p95 회귀 폭(+20% 기준)을 판정
3. 지급 Worker를 켠 운영 조건에서 확인. finance-mock 100ms는 접수가 열려 있고 알람이 없는지, 500ms(또는 Worker 정지)는 접수는 열린 채 작업 적체·지급 지연 알람이 나는지
4. 단위 테스트: (a) 운영 설정이 만드는 필수 관측 집합에 `settlement.payout_jobs` 키가 없음. 지금은 집합이 설정 Bean 안에서 바로 만들어지므로 집합을 만드는 부분을 분리하거나 Spring 컨텍스트 테스트가 필요합니다. (b) `payout_jobs` 도래 지연 65초 표본이 들어와도 gate를 닫거나 재개를 막지 않음

남는 결합: `PrometheusAdmissionMetrics`는 필수 여부와 관계없이 `financial_queue_*` 시계열을 모두 읽고, 음수·NaN·중복 값이나 중복 시각이 있으면 관측 실패로 gate를 닫습니다. 형식이 깨진 `payout_jobs` 시계열은 여전히 gate를 닫을 수 있습니다. 조회 선택자를 필수 대상으로 좁힐지는 구현 때 정합니다.

채택하면 [업무 정책](../policies.md#신규-접수-제한과-재개)에서 세 곳을 고칩니다. 중단 조건 표의 "소유 서비스별 미완료 Outbox·금융 Inbox·금융 Job" 행에 지급 작업 제외를 밝히고, "알림 전용 그룹·Job" 제외 문장에 지급 작업을 추가하고, 필수 대기열 목록에서 `settlement.payout_jobs`를 뺍니다. ADR 0007 D2에는 이 결과를 연결합니다.
